# Krose：紧凑音色库的组织建议

日期：2026-11-01。以下是研究结果和拟议设计，尚未替换当前运行资源格式或实现磁盘流播。继续使用 iPlug2。

## 产品范围

建议做一套共享的采样/合成引擎，承载多个乐器家族和大量轻量参数预置；优先保留特征波形、力度、包络、滤波和关键效果。音色浏览、分类、收藏和宏控可以借鉴 Analog Lab，深度按选定音色逐项补齐。

[Arturia 官方说明](https://support.arturia.com/hc/en-us/articles/11103298543772-Analog-Lab-Different-Versions)将 Analog Lab 定义为预置音色库及快捷控制入口，并将深入乐器编辑列为配合 V Collection 的能力。因此“像 Analog Lab 的使用方式”与“完整模拟整台工作站”应分别决定；浏览器形式不规定声音引擎必须怎样实现。

## 现有数据支持共享

本轮读取已恢复的 768 条原始 Program：每条 2140 字节，全部原始参数记录仅 **1,643,520 字节（1.567 MiB）**，不含额外可读标签/索引。726 条非鼓 Program 的活动 OSC/已开启槽共计 2445 次单声道 ROM multisample 引用，只涉及 398 个不同目录项；立体声按左右目录项计数，鼓组不在此统计中。该数字是引用关系，不能换算成 PCM 字节节省比例。

例如 `KROSS Piano-mf-L` 被 35 条 Program 引用，`Saw-MG3` 被 24 条引用。新增使用同一波形的预置只需添加控制和效果配置，不必重复存一套音频。当前 Concert/Warm/Wide 已共享同一份采样。

## Concert 存储实测

`tools/analyze_resource_budget.py` 对全部 84 个立体声样本核验来源哈希，重新解码原压缩码，并做 FLAC 编解码往返。均逐字节比较 **PCM 音频负载**；FLAC 未保留 WAV 中的 smpl/RIFF 元数据，循环、根音等必须另存映射。

| 方案 | 字节／大小 | 验证和边界 |
| --- | --- | --- |
| 当前运行采样包 | 102,683,978 / 97.927 MiB | 当前已使用，含包头/映射 |
| 84 个 WAV | 102,690,666 / 97.933 MiB | 含 RIFF/smpl 元数据 |
| FLAC 1.5.0，level 5 | 57,673,485 / 55.002 MiB | 84/84 解码后 PCM24 与原 WAV 相同；不含另存映射 |
| 现有原预测压缩码 | 34,227,086 / 32.641 MiB | 168 条 mono 源重新解码，84/84 拼成立体声后与现有 PCM24 相同；还需表、系数、映射和容器 |

保留原压缩码约可省三分之二音频体积，含义是**相对当前已接受声音没有再次引入损失**，不是声称 KORG 初次编码无损。预测状态检查点按每4096个 mono 码保存两个 int32 历史值，估算额外 67,536 字节；只估算大小，尚未实现/验证随机跳转和循环时的状态恢复。

这只测了 Concert 这套可用数据，不能由此推定全原机 ROM 的编码、压缩比或总安装大小。KORG 的约128MB是线性PCM等效容量。

报告：`research/derived/verification/resource-layout/resource-budget.json`；共享表：同目录 `factory-wave-sharing.csv`。临时 FLAC 和编译库仅放 `build/resource-layout/`，不替换产品资源。

## 建议的数据层

| 层 | 内容 | 节省方式 |
| --- | --- | --- |
| Preset | 名称、分类、OSC、包络、调制、FX和宏控；引用稳定的资源 ID | 一个波形家族派生多个预置，仅存参数差异或完整小记录 |
| Multisample map | 键区、力度区、根音、pitch、循环点、增益；引用 wave ID | 不复制同一音频；立体声保持明确配对 |
| Wave store | 按音频内容与格式指纹去重的压缩块，带校验、codec版本及索引 | 相同样本跨预置/库只存一次，独立块便于读取 |
| Runtime cache | 当前需要的解码 float 数据、预取队列、引用计数 | 同一宿主进程的插件实例共享；控制内存占用 |

身份不能只看文件名；去重键须包含真实音频及编码/位深/声道等解释信息。循环点、根音与映射保持独立，同一波形允许被不同预置以不同方式使用。固定打包顺序、格式版本和 SHA-256 继续遵守当前显式研究→assets 导出边界。

产品二进制与音色包分开；按家族选装的小包通过索引引用公共 wave store。音色包尚未存在或不完整时，浏览器应能说明缺少哪个包。此为建议，不在本轮安装/打包。

## 实现顺序

1. 先实现压缩资源读取，切换音色时在后台解码所需波形家族，共享已解码数据；音频线程不执行文件 I/O、解码、分配或阻塞锁。原 PCM24 包保留回退。当前约131MiB的解码 float 内存不会仅因磁盘压缩而自动缩小。
2. 库变大后再加块流播、起音预载、循环区常驻和有界缓存；异步切换保留旧语音资源直到释音结束。需要验证快速切换、多实例、离线导出、低缓冲与缺块处理。
3. 对简单周期波形可另做振荡器/小波表近似，减少素材；钢琴/弦乐保留必要采样。逐项听感验证，不能把合成替代标成原 ROM 音频。

块压缩、共享和流播是成熟思路：[FLAC 官方格式](https://xiph.org/flac/documentation_format_overview.html)提供独立帧与seek metadata；[HISE sampler 文档](https://docs.hise.audio/hise-modules/sound-generators/list/streamingsampler.html)展示 SampleMap/Monolith/流播的组织。这里只借鉴设计，未引入 HISE；其 HLAC 的16bit与 Full Dynamics处理也不能当作任意PCM24逐位无损的保证。

优先完成共享和不额外损伤当前音频的压缩；删减力度层、稀疏键区、降位深等改变声音的手段另行评价。本轮没有改现有声音，也没有实现、复制或安装新版插件。
